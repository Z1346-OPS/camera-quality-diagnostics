## 2. 对 A14 的独立判决

stage-35 §5 把 A14 整体标为「通过」。逐对象核对后应拆成三档：

| 保护对象 | 外部 oracle | 判决 |
|---|---|---|
| `data/samples/`（56）、`data/manifests/`（3）、`src/metrics.py` 等 4 个源码文件 | ✅ git 基线 `afdca8f` | **可证且已证**：`git diff` 为空。此证据比「实施前后各算一次哈希」**更强**——git 的 blob 哈希不可事后篡改，也不依赖执行者在实施前记得跑快照 |
| `photo/`（16 个文件） | ❌ 被 `.gitignore` 的 `/photo/` 排除 | **弱证据**：全部文件 mtime ≤ `2026-10-09 15:53`，早于基线提交时间 `2026-10-12 18:31`。作为对照，`src/quality_analysis.py` 的 mtime 在实施期间确实被更新过。mtime 可被保留或伪造，**不构成证明** |
| `data/reports/` 历史报告 | ❌ 被 `.gitignore` 排除，tracked 数 = 0 | **无证据**。而且 stage-35 §5 的保护对象清单里**根本没有列 `data/reports/`**，但规格 §4.2 A14 正文与 §5.1 都把它写进了保护范围 |

**精确结论：A14 不是「证据不足」，而是「部分超出可证明范围」。**
缺口只在两个 git 覆盖不到的区域，**不需要重做全部哈希**。

## 3. 关键修正：git 已经是 tracked 资产的前置快照

原提议是「任务模板增加实施前证据：保护文件列表 + SHA256 快照 + pytest 数量 + git commit」。
按本次实测，这条规则可以更省事也更可靠：

> **能被 git 追踪的，让 git 当 oracle；只有 `.gitignore` 排除的对象才需要手工快照。**

理由：

- tracked 资产的「实施前状态」已由基线 commit 完整、不可篡改地保存。手工快照是重复劳动，而且**依赖执行者在实施前真的记得跑**——这正是本次缺口的成因。
- gitignored 资产没有任何历史记录，**必须**在实施前显式快照，否则事后不可追溯。
