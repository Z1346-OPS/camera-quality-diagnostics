# Stage 23 三场景采集标签顺序检查

## 目标、输入与输出

输入一个由 `export_pairs.py` 生成的批次 JSON；输出该批次是否恰好按帧号顺序保存了 `white_paper`、`colored_object`、`white_restored` 各一条。检查只读，不改原始 CSV、配对 JSON 或摄像头程序。它不能识别镜头前真实放置的物体，也不验证光照、位置和曝光状态。

## 实现思路与原因

`validate_capture.py` 先复用 `summarize_pairs()` 校验 JSON 格式、帧号、标签和指标，再按 `frame_count` 排序比较标签序列。这样能发现重复按 `s`、漏保存、使用 `unspecified` 或标签顺序错误。按帧号而不是 JSON 中的排列顺序比较，是因为帧号才代表采集先后。标签顺序通过只说明记录结构符合协议；操作者仍须确认按 `2` 时确实换上彩色物体。

## 实际验证

- 聚焦测试：`6 passed`，覆盖正确顺序、JSON 乱序但帧号正确、重复或缺失标签、错误顺序、无效格式和只读性。
- 全量测试：`121 passed`。第一次测试因 pytest 默认临时目录访问被拒而在准备阶段出现 6 个错误；改用当前可写工作区的独立临时目录后测试通过，未修改或弱化测试。
- 实际运行：批次 `7bfd31a24dc64d96aa22311a78bf7200` 返回 0，报告三标签顺序符合流程；只有 `unspecified` 标签的批次 `f1c6d22b952147bf91a2b3ac7c0cbc9b` 返回 1，并显示期望与实际序列。这两个结论只涉及记录的标签。
- 项目未配置独立 build、lint 或类型检查；本阶段未打开真实摄像头。

## 易错点、练习与掌握评价

- “标签通过”不等于“实际场景通过”。此前白纸被误标为彩色物体的批次，即使标签顺序正确，仍应由操作者排除。
- 同一次多按 `s` 不是多次独立实验；本检查按本项目当前“一场景一条”的采集协议处理。
- 返回码 1 表示这份记录不符合三场景协议，不表示相机硬件坏了。

练习：①为什么按帧号排序？②四条记录里白纸重复一次会怎样？③标签顺序通过后，还需人工核对什么？

四级掌握评价沿用项目原标准：能看懂、能自己解释、能修改已有代码、能脱离原代码写类似逻辑。本阶段功能及测试由助手实现，用户的独立掌握等级尚未评估。

面试可如实说：“我为三场景采集增加了只读流程核对，防止漏保存、重复保存和标签顺序错误。它复用配对报告的格式检查，再按帧号比较记录的标签；我没有把标签正确误当成真实画面或摄像头状态已验证。”

下一步是获得更多条件明确、独立运行的真实样本，再评估指标的重复性；目前不设置故障阈值。
