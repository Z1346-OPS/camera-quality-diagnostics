# Stage 20 按批次核对报告

## 目标与缘由

全量 `check_reports.py` 会报告历史上两条只有颜色数据的记录，这是正确的全历史结果。但要判断一次新采集是否完整，还需要只显示指定 `run_id` 的配对情况。本阶段给现有校验命令增加可选的 `--run-id`；不带选项时仍检查全部历史，不删除或修改 CSV，也不改变故障判断规则。

## 输入、输出与实现

输入是质量和颜色 CSV，以及可选的 32 位小写十六进制 `run_id`。程序先读取并校验两份完整 CSV 的表头、字段和关联键，再筛出目标批次。这样历史未配对记录不会混入本次统计，但历史坏行或重复键仍会报错。输出为匹配、仅质量、仅颜色的条数和缺项键；匹配完整返回 0，有单侧记录返回 1，ID 无效、批次不存在或 CSV 错误返回 2。

在项目根目录运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 .\src\check_reports.py --run-id 7bfd31a24dc64d96aa22311a78bf7200
```

省略 `--run-id` 就恢复原来的全量检查。只读模式不会自动修复旧报告；两种结果的检查范围不同，不能把指定批次通过说成全部历史通过。

## 修改与验证

- `src/check_reports.py`：增加可选批次筛选与输入校验，保留原有全量行为。
- `tests/test_check_reports.py`：覆盖完整批次、指定批次缺项、不存在或无效 ID，以及历史坏行不能被筛选隐藏。
- `README.md`：补充指定批次命令。

语法检查通过，完整测试 `110 passed`。用真实批次 `7bfd31a24dc64d96aa22311a78bf7200` 运行指定批次命令，返回退出码 0：“匹配 3 条；仅质量 0 条；仅颜色 0 条”。同一份真实报告不带 `--run-id` 时仍返回退出码 1：“匹配 14 条；仅质量 0 条；仅颜色 2 条”；两条仅颜色记录均为旧批次。两种结果范围不同，均符合预期，旧记录未被删除。摄像头实时画面不受此改动影响。

## 易错点、练习与掌握评价

易错点：不能在读取 CSV 前直接跳过其他批次的行，否则其他批次的坏行可能被隐藏；也不能把“所选批次没有记录”误判为“匹配成功”。

练习：①为什么默认全量检查仍会返回 1？②指定批次有一条仅颜色记录时应返回什么？③为什么过滤要发生在完整 CSV 校验之后？

四级掌握评价沿用项目原标准：能看懂、能自己解释、能修改已有代码、能脱离原代码写类似逻辑。前三项需结合用户复述和练习评估，第四项尚未验证。

面试可如实说：“我发现全量历史报告包含功能启用前的单侧记录，于是为校验器增加按批次查看的方式，同时保留全量检查和错误校验。指定批次通过只说明该批次已保存的质量与颜色记录配对，不等于证明摄像头质量合格。”
