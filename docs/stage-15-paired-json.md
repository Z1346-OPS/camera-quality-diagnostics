# Stage 15 按批次导出配对 JSON

## 阶段目标与输入输出

输入：两份带 `run_id` 的质量、颜色 CSV，以及一个指定的 `run_id`。输出：`data/reports/camera_pair_<run_id>.json`，每个帧号包含一组质量指标和颜色指标。本阶段只整理数据，不做故障识别、阈值标定或 RAG 检索。

## 关键流程及原因

先复用 Stage 14 的关联键校验，再选出指定批次。若该批次有单侧记录或没有配对记录，立即失败，不生成 JSON；其他历史批次的单侧记录不会混入本批次。随后读取所选批次的指标，将 CSV 文本数值转换为有限 JSON 数字，按帧号排序并写入新文件。使用独占创建模式 `x`，避免重复运行覆盖已有结果。原 CSV 始终只读。

JSON 保留质量和颜色各自的 `recorded_at`，因为两次写入时间可能相差毫秒。`schema_version` 供后续读取方识别格式，`record_count` 是导出帧数，不是摄像头总帧数。运行时应先退出摄像头程序，避免边追加 CSV 边导出。

## 实际验证

2026-09-29，自动测试涵盖指定批次筛选、历史其他批次单侧记录、所选批次缺项、无记录、已有 JSON 不覆盖、非法数值与非法批次 ID；完整测试 `82 passed`。真实批次 `f1c6d22b952147bf91a2b3ac7c0cbc9b` 导出成功，JSON 内有 1 个配对帧（帧 93），亮度 97.8、通道差 1.7。导出前后对两份源 CSV 进行了哈希检查；导出程序以只读方式打开它们。无摄像头运行测试：这是离线导出阶段，不需要打开摄像头。

## 易错点、练习与掌握评价

- `run_id` 不能省略：不同运行会从帧 1 重新计数，仅凭帧号会错配。
- 历史其他批次的单侧记录不等于当前批次不完整；当前批次若有单侧记录则拒绝导出。
- 已有 JSON 不覆盖；若需重做，先人工确认目标文件，再决定保留或另行处理。
- 练习：解释为何质量和颜色各留一个时间戳；说明 CSV 中的 `"97.8"` 与 JSON 中的 `97.8` 有何区别；说出独占创建模式防止了什么。

四级掌握评价：代码由助手实现；用户是否能看懂、解释、修改或独立重写，均待用户实际练习，不代填等级。
