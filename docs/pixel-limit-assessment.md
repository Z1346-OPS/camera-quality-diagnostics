# 阶段 1：提高像素上限的评估

日期：2026-10-02。用户提出适当提高上限，并要求客观全面评估。本次已完成只读检查与隔离基准测试，**未修改生产入口的 12000000 像素上限、25 MiB 文件上限或 EXIF 接受规则**。推荐方案尚待决定。

## 触发原因与收益

用户提供的 `A1.jpg` 是 JPEG/RGB、3072×4096（12582912 像素）、2937959 字节。它的尺寸比当前上限高约 4.86%，由此触发策略拒绝。当前上限是资源策略，不能当作 JPEG 解码器的能力边界，也没有业务证据要求必须恰好取 12000000。提高至 16000000 能容纳此尺寸，并为更大的输入留一定余量；图片保持原分辨率，不引入降采样对后续细小二维码读取的影响。

提高上限不会证明照片更清晰或读码更准确，也不会自动解决其他输入错误。不能仅以某张图片成功为理由放开任意尺寸。

## 当前实现的开销与测量方法

检查实际安装的 Pillow 源码，`ImageOps.exif_transpose` 在默认模式下返回新图，即使无方向变换也返回副本。当前流程还包含 RGB/透明度合成、NumPy 数组、BGR、灰度、直方图和 64 位 Laplacian 中间数组。峰值内存随像素数与模式增加，压缩字节数不能代表解码后内存。透明 RGBA 图比 RGB 图有更多中间缓冲；未来可研究减少复制，但本次未改算法或释放顺序。

测试使用现有 Python 3.12.10 虚拟环境、Windows 11 26100、20 个逻辑 CPU、约 15.64 GiB 物理内存。可用物理内存在评估附近约 3.8–4 GiB，随其他程序变化；具体 CPU 型号的 CIM 查询被权限拒绝，未以未知型号做性能结论。系统提交量上限约 33.64 GiB，不等于物理内存；提交量还反映需要 RAM 或页面文件支持的分配。

每个样例用全新、独立 Python 进程运行 3 次。仅在基准进程里将模块 `MAX_PIXELS` 临时设为 24000000；原图、仓库源码和已有报告保持不变。样例包括实际 A1 文件、RGB/RGBA PNG、方向值 6 的 JPEG、与 A1 等尺寸且方向有效的合成 JPEG、固定随机种子的纹理 JPEG。合成图用于资源测量，不代表真实手机拍摄效果或标签读码表现。

进程内部用 Windows 内存计数器记录峰值工作集和峰值提交量，避免测到虚拟环境启动器。图片分析时间与整进程时间分开；报告时间为 3 次中位数，内存为 3 次最大值。测量是本机串行运行，没有统计 P95、并发负载、其他平台或所有模式的最坏情况。

评估脚本设采样保护：工作集超过 800 MiB、提交量超过 1400 MiB 或运行超过 15 秒时停止该评估进程；可用物理内存不足 1.5 GiB 时停止批次。它是实验保护措施，采样和线程调度存在延迟，**不是产品的硬内存/硬超时保证**。

首轮测量遇到子进程错误信息编码问题；修正 UTF-8 后暴露了 A1 的 EXIF 拒绝。另一轮初始实验保护把提交量也限制为 800 MiB，导致原有 12M 对照样例被停止；这说明实验预算设置过小，不等于程序内存不足。核对工作集、提交量与系统余量后，保留 800 MiB 工作集保护，单独将实验提交预算设为 1400 MiB，再完整重跑取得表中数据。失败轮次未混入完成样例统计。

## 新发现：A1 的方向值为 0

当前入口只接受方向值 1–8，而 A1 文件返回 0。因此只改像素上限，下一步仍会被方向校验拒绝。实际安装的 Pillow `exif_transpose` 对未映射到 2–8 的值不执行旋转；这只能说明库如何处理，不能证明该照片真实方向正确。

可单独评估的兼容规则：保留 `original_exif_orientation: 0`，按“方向未指定、不旋转”分析，并在结果明确写入警告，要求用户复核显示方向；1–8 仍正常处理，其他不受支持值仍报错。不能把原始值 0 静默改记为 1，不能根据尺寸猜测拍摄方向。本次没有实施这条规则，也未重写原图 EXIF。

## 方案比较与建议

| 方案 | 收益 | 代价与适用边界 |
| --- | --- | --- |
| 保持 12M | 不改变现有资源策略 | 会继续拒绝 A1 这类略超限输入，要求另拍或显式处理副本 |
| 提高到 16M（建议） | 覆盖 12.58M 输入；原始分辨率保留；当前本机单进程测试有余量 | 本机 RGBA 样例峰值工作集约 474 MiB，不能直接移作服务并发默认值 |
| 提高到 20M/24M | 接受更大输入 | 已测工作集与提交量进一步增长，当前业务尚未展示必须接受这些尺寸的收益 |
| 用户显式生成分析副本 | 可限制分析像素；保留原件 | 要记录缩放、确认细小码影响；先全尺寸解码再缩小并不能消除初始解码峰值 |

建议本地阶段选择 **16000000 像素、继续 25 MiB、串行使用**。同时记录实际尺寸、限额与配置哈希；超限错误提示补充宽×高、实际像素和允许值。50M、100M 等输入没有实测，不从表中外推承诺支持。若后续要服务化，需根据服务器 RAM、页面文件/提交余量、并发数和耗时重新制定策略；必要时采用可终止进程与实际资源限制。

采用建议后的最小实施范围为 `src/analyze_image.py`、对应测试、README 与阶段记录：更新版本标识；补测新上限前/等于/超过上限；旧上限附近的有效图转为可接受；维持异常输入和原图/旧结果保护；用新结果文件验证 A1，并分别确认像素策略与方向警告。运行新入口测试、完整回归、实际 CLI 冒烟及差异检查。像素上限和 EXIF 0 接受规则是两项独立变化，不能用提高上限掩盖方向问题。

本次交付为评估结论，尚未修改接受规则。A1 的手机实拍来源与实际显示方向仍待用户明确确认。
