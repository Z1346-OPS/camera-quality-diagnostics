# Stage 12 运行批次标识

## 目标和输入输出

每次启动摄像头生成一个 `run_id`；同一次运行保存的颜色记录共用此 ID，不同运行使用不同 ID。输入是摄像头按键保存流程，输出是新文件 `data/reports/camera_colors_runs.csv`，比阶段 10 的报告多一列 `run_id`。汇总程序读取新文件时按批次和场景分组。

## 关键流程与设计原因

成功打开摄像头后使用标准库 `uuid4().hex` 生成一次 ID；按 `s` 将它和当前帧颜色数据一起保存。帧号每次重启都会从 1 开始，所以不能用帧号区分运行。32 位十六进制随机 ID 不依赖系统时间是否被修改，重复风险极低，但不应称为数学上绝对唯一。

为避免给旧 `camera_colors_labeled.csv` 追加不同列，新记录写 `camera_colors_runs.csv`。历史文件保留原样；旧默认汇总命令继续读旧文件，新报告需要显式指定路径。报告函数在追加前检查表头，并限制标签和 ID 格式，避免把无效数据写进 CSV。

旧报告没有 `run_id`，不能可靠地反推以前的运行批次，故不自动迁移。新报告只覆盖颜色指标；质量报告仍没有 `run_id`，跨运行不能仅用帧号连接两份报告。

## 验证与真实结果

自动测试覆盖同次多帧共用 ID、不同 ID 的同名场景分开汇总、旧文件不变、表头与非法 ID 处理。`python -m compileall -q src tests` 通过；相关测试 `30 passed`，完整测试 `62 passed`，`git diff --check` 通过。项目没有配置独立 build、lint 或类型检查。

旧真实报告仍可用默认汇总命令读取，输出与上一阶段相同。新命令行通过临时 CSV 冒烟测试：两个不同 ID 的白纸记录分别输出为两行，且读取前后内容未变化。临时数据不是摄像头实测。

2026-09-28 用户完成两次实际摄像头采集并运行批次汇总。读取原始 CSV 核对结果：第一批 `5df64a2060124fd89c8ff81143719db3` 的帧号 480，通道差 0.3；第二批 `980d092eddf048f2a096cda9bce3c30b` 的帧号 338，通道差 1.5。程序将两个不同 `run_id` 分成两行，符合批次隔离目标。汇总前后文件 SHA256 一致，未改写报告。

两条实际记录的 `scene_label` 都是 `unspecified`，并非计划中的 `white_paper`。用户提供的只有汇总输出，没有按键切换日志，无法判断是否未按 `1` 或画面窗口没有接收按键；不能把它们事后改称白纸场景。批次区分已经由硬件数据验证，白纸标签的本次按键操作未验证。

## 易错点、练习和掌握

- 新 CSV 出现前，显式读取它会提示文件不存在；请先启动摄像头、按 `s` 保存。
- 只按数字键切换场景，不会写 CSV；需要按 `s`。
- 打开多个程序窗口会产生不同批次；同一窗口内切换标签仍属于同批次。
- 文件被 Excel 占用时仍可能出现 Permission denied；先关闭查看程序，再重试，不随意修改权限。

可选练习：解释 `frame_count` 与 `run_id` 的不同；说明为什么不能直接给旧 CSV 加列；指出同批次白纸与彩色物体记录为何可以对照。

代码由助手实现；用户四级掌握程度未验证，不以自动测试结果代替。

## 面试表达

为摄像头采集记录加入运行批次 ID，解决多次启动后帧号重复、汇总结果混在一起的问题。为保护历史 CSV 使用新文件格式，并在读取时按批次和场景分别统计。该功能用于保证实验记录可追溯，不等于自动偏色检测。
