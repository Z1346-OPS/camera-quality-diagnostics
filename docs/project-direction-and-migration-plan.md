# 项目方向转变与渐进迁移计划

记录日期：2026-10-01。

本文件记录讨论后的项目方向、现有代码的复用方式和后续实施顺序。它是一份规划，不代表手机端、服务端、数据库或条码识别已经实现。本次仅新增说明文档及 README 入口。

**阶段 0 顺序更新（2026-10-01）**：最新的[标签读码项目设计与阶段清单](label-reading-project-design.md)将本地 ROI、QR 基线读码和独立评测移到手机服务之前，以先验证业务价值。本文件保留方向转变背景与原始迁移思路；下文“先服务、再读码”的步骤表已由新清单取代。当前服务和读码仍未实现。

## 1. 为什么调整方向

原项目从本机摄像头连通性测试开始，逐步实现图像指标、CSV/JSON、原始帧留证及数值复核。它解决了“能采集、能计算、能追溯”的基础问题。

用户提出了几个实际约束：

- 不方便携带笔记本到不同位置采集，希望用手机拍摄、上传和查看结果。
- 单纯白纸实验和指标变化不足以说明实际用途，需要关联一个具体任务。
- 数据存储要有真实项目的组织方式，能查询历史、备份和恢复。
- 程序升级出问题时，需要能定位修改并执行经过验证的回退方案。
- 要考虑 Windows、macOS、Linux，而不是把 Windows 摄像头程序直接当成服务器。

据此，将下一阶段方向聚焦为：**手机端标签图像采集与可读性检查工具**。优先以带条码的商品或包装标签作为具体任务，后续再评估文字识别等扩展。

## 2. 要解决的具体问题与预期成果

用户拍到一张标签照片后，希望知道编码是否被读出、结果是否正确、哪些图像现象值得检查，并能比较重新拍摄后的变化。

拟实现的流程：

```text
手机拍摄或选择图片 → 上传并创建任务 → 保存原图
    → 处理图片方向、确定目标区域 → 计算质量指标、尝试条码解码
    → 保存分析结果与版本 → 手机查看结果和历史 → 重拍后比较
```

应用价值通过“已知编码是否正确读出、重拍后是否改善、异常提示的误报和漏报”验证。仅显示清晰度或亮度数值，还不足以证明能辅助实际工作。条码解码成功不等于获得工业条码质量等级；数值变化也不能自动确定相机故障原因。

手机拍摄实物时，评价的是这张手机照片。若以后要排查工业相机成像，应接入工业相机原始图片；手机拍摄现场环境的照片属于另一类辅助证据。两种来源要分别记录。

## 3. 当前真实基线

代码基线：Git 提交 `9fab64c`，即本次方向文档之前的 README 更新版本。

已经实现：本机摄像头采集、指标计算、人工场景标签、CSV/JSON、会话信息、可选原始 PNG、单帧与批次复核。此前最近一次完整自动测试结果为 150 项通过；该结果描述旧版功能的验证，不代表新方向已经通过测试。

尚未实现：手机网页上传、Web API、数据库持久化、用户权限、条码解码、目标区域交互、服务部署、数据库升级与恢复演练、RAG。macOS/Linux 的实际兼容性也尚未完成验证。

## 4. 原代码是否需要修改

结论：需要渐进调整，继续采用“保留旧入口、新增模块、逐步迁移”的方式。现有实现作为可运行基线和回归测试依据。

| 现有文件或能力 | 处理方式 | 原因与后续改动 |
| --- | --- | --- |
| `src/metrics.py` | 优先复用 | 已接收 NumPy 图像数组，不依赖摄像头窗口；服务入口需先统一方向、数据类型、颜色通道和目标区域 |
| `src/camera_test.py` | 保留本地入口 | 打开设备、显示窗口和按键适合本机使用；服务器分析流程应直接调用指标函数 |
| `src/report.py` | 保留 CSV 能力 | 后续数据库负责查询和持久化，CSV 作为导出；不将已有 CSV 当作数据库反复改写 |
| `src/frame_evidence.py` | 保留旧采集留证 | 手机上传需增加原始文件保存逻辑，不能把所有上传文件直接当作摄像头 PNG |
| `src/session_metadata.py` | 保留旧版含义 | 现有编号、后端名称属于本机摄像头；手机来源与上传信息另设数据结构，未知信息留空 |
| `src/export_pairs.py`、各汇总脚本 | 保留历史报告处理 | 不强行给历史报告补造手机信息、用户或算法版本 |
| `src/verify_frame_metrics.py` | 后续解耦配置 | 当前从 `camera_test.py` 导入阈值；服务化时应移到共同配置层，并保存每次分析实际使用的配置 |
| `tests/` | 保留并扩展 | 继续验证旧功能，再增加图片上传、数据库、解码、权限和部署测试 |

手机图片可能包含 EXIF 方向、不同分辨率、压缩或自动曝光差异。第一版拟支持明确列出的 JPEG/PNG 输入，其他格式返回清楚提示；HEIC 等支持需单独确认依赖并测试。分析前统一方向并保留原图，记录实际分析区域和预处理参数。不同设备、目标大小和构图的分数不能直接套用同一判定阈值。

## 5. 拟采用的技术与参考项目

技术栈指各层实现所用的技术组合。以下是计划选型，尚未安装或接入。

| 层次 | 计划选型 | 本项目中的职责 |
| --- | --- | --- |
| 手机界面 | 响应式 HTML/CSS/JavaScript | 拍照或选择文件、上传、查看结果与历史；复杂前端框架后续按需要选择 |
| 服务接口 | Python + FastAPI | 接收任务、校验输入、调用分析、返回 JSON |
| 分析 | OpenCV + NumPy；必要时使用 Pillow | 图片方向与格式处理、目标区域、现有质量指标 |
| 业务验证 | ZXing-C++ 的 Python 接口 | 尝试解码，记录编码类型、内容、位置及是否符合已知答案 |
| 数据库 | PostgreSQL + SQLModel + Alembic | 服务化版本的数据模型、查询和结构迁移；SQLModel 基于 SQLAlchemy 等组件 |
| 图片 | 首先采用服务器文件目录 | 保存原图及衍生图；通过存储接口为以后对象存储留出替换位置 |
| 版本与部署 | Git、固定依赖、Docker Compose | 明确发布版本、运行配置和持久化目录 |
| 验证 | pytest；后续增加 CI | 功能回归、服务测试、平台兼容性检查 |

参考资料（2026-10-01 已做仓库、文档和部分源码阅读，未部署这些项目）：

- [FastAPI 官方全栈模板](https://github.com/fastapi/full-stack-fastapi-template)：参考后端组织和数据模型；[后端说明](https://github.com/fastapi/full-stack-fastapi-template/blob/master/backend/README.md)展示 Alembic 迁移流程。其完整前端不是本项目当前承诺采用的方案。
- [Immich](https://github.com/immich-app/immich)：参考手机图片管理；[备份说明](https://docs.immich.app/administration/backup-and-restore/)区分文件与数据库；[升级说明](https://docs.immich.app/install/upgrading/)明确其不支持直接降级，提醒本项目必须设计和验证自己的回退边界。
- [CVAT](https://github.com/cvat-ai/cvat)：参考图片任务、目标区域标注和人工复核；其标注质量与本项目的拍摄质量是不同概念。
- [ZXing-C++ Python 接口](https://github.com/zxing-cpp/zxing-cpp/blob/master/wrappers/python/README.md)：参考 OpenCV/NumPy 图片接入条码解码的方式。

参考设计不等于整套复制。实际引入依赖或代码时，要核对选定版本、许可证、平台支持和安装要求。

## 6. 数据存储与追溯设计

建议将任务、图片、分析结果分开。一个任务可以包含多张图片；一张图片可以有多次分析结果。重新分析新增结果，保留旧结果便于比较。

| 对象 | 计划记录的信息 |
| --- | --- |
| 检查任务 | 任务 ID、创建时间、用户、场景说明、状态 |
| 图片 | 图片 ID、任务 ID、来源、存储键、校验值、尺寸、上传时间；拍摄时间和设备信息仅在实际可获得时记录 |
| 分析结果 | 图片 ID、算法版本、配置版本、预处理与区域信息、指标、解码结果、耗时、状态与错误信息 |
| 参考与复核 | 正常参考图片、已知编码答案、人工判断、重拍关联和备注 |

原图、缩略图、标注图使用不同位置。数据库保存关联和位置，避免把服务器绝对路径作为对外接口。文件写入与数据库事务不是同一个原子操作，实施时需要明确上传中、完成、失败状态，并处理重试和中途失败，避免出现无文件记录或无人管理的文件。

备份必须同时覆盖数据库、原图以及恢复需要的配置与版本信息，并在隔离环境做恢复验证。原始用户图片、运行数据库和凭据不提交 Git；现有 `.gitignore` 只覆盖部分旧报告目录，新增存储目录前应同步补充忽略规则。

## 7. 升级与回退如何安排

- 代码修改通过 Git 保存；开发期撤销已提交的错误修改可使用 `git revert`，保留历史。
- 发布时固定程序版本、依赖和部署配置，并记录对应数据库迁移版本与算法配置版本。
- 数据库结构变化使用 Alembic 迁移文件。存在 `downgrade` 函数也不意味着被删除的数据能恢复。
- 旧程序兼容现有数据库时，才可以切换到上一份程序；破坏性结构变更需另做恢复方案。
- 从备份恢复可能丢失备份之后新增的数据，要在演练中验证和说明，不能将其称为无损回退。

后续验收应包含一次正常升级和一次故障回退演练。当前只有 Git 基线，尚未完成服务发布或数据库恢复验证。本文件本身不执行任何回退或数据迁移。

## 8. 手机使用与跨平台边界

开发阶段可由笔记本提供局域网服务，手机与它在同一网络内使用；笔记本关机时服务不可用。异地使用和笔记本关机后继续使用，需要另行部署服务器，资源和费用待选定。

手机端先支持拍照或选择相册后上传；断网时可先用系统相机保存照片，再联网上传。网页内实时相机、自动离线同步和原生 App 不属于首个可用版本。

Python 核心避免写死盘符，使用可配置存储路径。Web 分析模块避免依赖桌面窗口；Windows 的 DirectShow 后端留在本地摄像头入口。Docker 可固定部分运行环境，但不替代 Windows/macOS/Linux 及 x86/ARM 的实际验证。计划先稳定一种服务器部署环境，再扩展平台测试。

## 9. 迁移顺序与验收

按完整可使用成果推进，不按新增脚本数量衡量进度。

| 步骤 | 实施内容 | 验收证据 |
| --- | --- | --- |
| 1. 通用图片分析入口 | 输入图片，统一方向和格式，调用现有指标；解耦阈值配置 | 合成样例和真实手机图片均有结果；旧指标测试仍通过；异常输入有明确错误 |
| 2. 最小服务闭环 | 手机上传、任务和原图持久化、分析结果、历史查询；加入基本访问控制 | 手机实际上传并查看结果；程序重启后仍能查询；失败上传和重复请求有明确处理 |
| 3. 标签可读性任务 | 接入解码和目标区域，记录已知编码及重拍关系 | 展示正确解码、未解码或错误解码的真实案例，不能用“分数高”代替业务验证 |
| 4. 条件与效果验证 | 设计光照、模糊、角度等样本；以独立采集批次做验证 | 记录样本划分、正确解码情况、提示误报漏报、重拍前后结果 |
| 5. 部署与恢复 | 固定发布、数据库迁移、备份、兼容性与回退演练 | 能按说明启动，并演示恢复后图片与数据库关联完整 |

第一版不承诺自动定位工业相机根因、识别所有故障、支持所有手机格式或完成 RAG。RAG 在结构化结果和排查场景稳定后再接入。

## 10. 学习重点与分工

学习顺序：Python 模块和异常处理 → HTTP/JSON/文件上传 → 基础网页与接口调用 → SQL 和事务 → Git 发布与数据库迁移 → Linux/Docker 部署。

助手负责分阶段实现、测试和提炼重点；用户负责真实手机操作、拍摄条件确认、业务结果复核，以及解释关键流程。程序完成与个人独立掌握分开记录。

每阶段需要回答：解决谁的什么问题、输入和输出是什么、如何验证、失败时如何定位。自测问题：为什么原图与分析结果分开？为什么 Git 回退不能代替数据库恢复？为什么手机图片不能直接证明工业相机成像正常？

当前可用于介绍项目的表述：已经完成本地采集和指标追溯，现计划将指标核心接入手机上传服务，以标签解码结果检验图像分析的实际价值。手机服务和数据库功能完成之前，不把它们写成既有成果。

尚需在对应实施阶段确认：手机系统和输入格式、实际服务器环境、首批标签类型与已知答案、样本留存需求。这些未决信息不影响本次方向记录，但会影响实现与验收细节。
