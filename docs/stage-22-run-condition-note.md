# Stage 22 按批次保存人工拍摄条件

## 阶段目标与输入输出

前一阶段能比较三个运行批次，但拍摄条件散落在聊天记录中。现在增加一个独立命令，把操作者提供的原话与已有 `run_id` 绑定。输入是已保存的批次 ID 和人工条件备注；输出是 `data/reports/camera_conditions_<run_id>.json`。本阶段不自动测量光照、距离或曝光，不改摄像头流程、原始 CSV 和配对 JSON。

## 关键流程与设计原因

`record_conditions.py` 先要求非空备注，再复用 `reconcile_reports()` 校验完整 CSV 并确认所选批次的质量与颜色记录均配对。仅在校验通过后，用独占新建模式写入 JSON；已有同名文件不会覆盖。`run_id` 经现有 UUID 格式校验，不能把任意路径拼入输出文件名。

JSON 用 `source: operator_note` 明确标识人工陈述，`note_recorded_at` 是**填写备注的时间**，不是摄像头拍摄时间。未知的条件要如实写“未知”或“未测”，不能从图像指标倒推为已核实的曝光设置。此阶段只保存自由文本；后续如需按光照或距离做统计，必须先制定统一的结构化字段与采集方法。

以下是本次已执行的命令，供以后换成**新批次 ID 和当次真实备注**时参考。本批次备注已存在，直接重复运行会报“文件已存在”：

```powershell
.\.venv\Scripts\python.exe -X utf8 .\src\record_conditions.py 7bfd31a24dc64d96aa22311a78bf7200 --note '采集后回忆：按2时换上了彩色物体，其他条件基本没变。光照、位置和纸张距离未量化；自动曝光状态未核实。'
```

## 易错点、练习与掌握评价

- `run_id` 只是关联键；一条人工备注不能提升图像指标的测量准确度。
- `note_recorded_at` 是事后记录时间，不能当作采集时间。
- 同名备注已存在时命令报错，不应删除旧文件来制造“成功”。

练习：①为什么空备注不能保存？②为什么已有文件不自动覆盖？③如果不知道自动曝光状态，应该如何写，为什么？

四级掌握评价沿用项目原标准：能看懂、能自己解释、能修改已有代码、能脱离原代码写类似逻辑。工具和测试由助手实现；用户的四级实际水平尚未通过独立练习评估。

面试可如实说：“我把人工拍摄条件与运行 ID 分开记录，并明确区分操作者事后备注与程序测量值。程序先确认该批次质量、颜色报告配对，再创建不可覆盖的备注 JSON，避免把不完整数据或旧备注悄悄当成新结果。”
