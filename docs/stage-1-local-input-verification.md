# 新阶段 1：本地图片入口核验

日期：2026-10-02。代码实现和自动验证完成；真实手机照片验收待用户操作。仍只做本地图片分析，不启动 ROI、二维码解码或手机服务。沿用[主设计](label-reading-project-design.md)及[初次实现记录](stage-31-local-image-analysis.md)。

## 目标、数据流与原理

输入本地单帧 JPEG/PNG；按实际内容确定格式，限制字节数与像素数，检查 8 位模式和 EXIF 方向，再转正并统一为 BGR，复用原有质量指标。透明像素合成到白色背景；无 ICC 颜色转换、缩放或区域裁剪。输出保留未舍入指标、原件 SHA-256、预处理与配置，并能指出失败步骤。暗/亮像素比例只是灰度阈值统计，不等于真实曝光诊断。

原件只读；重新分析使用新的结果文件名。每次成功结果有独立 `analysis_id`、UTC 分析时间和 JSON `schema_version: 2`。原有 `source`、`preprocessing`、`analysis_config`、`metrics` 字段仍保留，旧版本 JSON 不改写。新增 `config_sha256` 对实际阈值、限额、允许格式/模式等配置计算哈希；`provenance` 保存实现标识、三份相关源码的 SHA-256、Python/OpenCV/NumPy/Pillow 版本和 Git 提交及工作区是否有未提交改动。仅 Git 提交不能代表当前未提交代码，故同时记录源码哈希；Git 不可用则记录 `unavailable` 和空值，不假称工作区干净。源码无法读取时对应哈希为空。

`analysis_duration_seconds` 记录图片读取、预处理和指标计算耗时，排除 Git 信息采集、JSON 渲染和结果文件写入。它不能代替独立评测的总耗时或 P95。当前 `source.path` 是本地记录；将来对外导出须移除内部路径。

- `tests/test_analyze_image.py`：从 12 项扩展至 39 项，覆盖八种 EXIF 方向的真实像素排列、通道与透明度、伪扩展名、截断文件、动画、上限边界、错误分类、追溯及旧结果保留。
- README、阶段 31 文档、主设计：关联本记录。公共阈值与旧摄像头/复核入口本次未改。

仍限制 25 MiB 和 1200 万像素，允许 `RGB/RGBA/L/LA/P`。不支持 16 位模式、CMYK、HEIC 等输入；动画 PNG 明确拒绝，避免默默只分析首帧。按编码内容检查格式，扩展名不同本身不会触发拒绝。超限只拒绝，不自动降采样；原图不复制或覆盖。

| 错误码 | 含义 |
| --- | --- |
| `input_not_found` | 输入文件不存在 |
| `input_access_denied` / `input_read_failed` | 没有读取权限 / 其他读取错误 |
| `file_limit_exceeded` / `pixel_limit_exceeded` | 文件字节 / 解码像素超限 |
| `unsupported_format` / `unsupported_mode` | 已识别但未允许的格式 / 通道或位深模式 |
| `unsupported_animation` / `invalid_orientation` | 动画输入 / 无效 EXIF 方向 |
| `corrupt_image` | 损坏、截断或无法识别为可解码图片 |
| `output_exists` | 结果名已存在，拒绝覆盖 |
| `output_access_denied` / `output_write_failed` | 输出权限 / 其他写入错误 |
| `resource_exhausted` / `analysis_failed` | 内存不足 / 其他分析失败 |

CLI 错误在 stderr 显示码和提示，不打印成功 JSON。内存不足的 CLI 错误分类不等于对所有资源建立硬限制。新结果写入过程中发生磁盘错误可能留下部分文件，需人工核查；旧文件不会被覆盖。后续服务需另做临时写入、状态与恢复机制。

## 学习练习与面试问答

练习：①找到尺寸检查与 `image.load()` 的先后关系，解释为何先检查；②用实际照片完成哈希/方向核对；③对照错误码说明超限、损坏、权限错误各如何处理。四级掌握评价沿用阶段 0 的“提示复述/按步骤操作/独立解释定位/设计实验复核”；当前用户掌握程度待验证。

1. **为什么需要错误码？** 30 秒：文字帮助用户理解，稳定码帮助程序区别超限、损坏和权限问题。进一步原理：输入策略与执行失败分开处理。证据：`AnalysisError.code` 与异常测试。局限：当前只提供 CLI 提示，尚无服务错误协议。
2. **为什么只保存 Git 提交不够？** 30 秒：未提交代码不属于 HEAD，必须记录 dirty 状态和实际源码哈希。进一步原理：仓库版本与运行文件可能不同。证据：`provenance` 三份源码哈希和 Git 状态。局限：还没有发布包或所有环境依赖的完整复现方案。
3. **为什么 EXIF 转正先于 ROI？** 30 秒：转正后显示坐标才与裁剪坐标一致。进一步原理：方向是坐标变换，不只是交换宽高。证据：八方向像素排列测试。局限：ROI 尚未实现，真实手机方向待验证。
4. **为什么限制像素而不只限制文件大小？** 30 秒：压缩文件小，解码后的数组也可能很大。进一步原理：内存主要随像素和中间数组增长。证据：小压缩文件的超限拒绝与 12MP 样例。局限：当前限额不等于硬内存或并发控制。
5. **指标变化是否说明标签可读性改善？** 30 秒：亮度和清晰度只是描述，需读码结果和独立真值评测。进一步原理：图像代理指标不能替代业务正确率。证据：当前只复用指标，不宣称读码。局限：阶段 2/3 的解码与评测未实现。
