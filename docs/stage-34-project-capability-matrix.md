## 3. 面试故事库（5 个，均可追溯到证据）

### 故事 1：为什么同一批二维码，有的读不出来

- **现象**：`photo/A7.jpg`（4096×3072 手机实拍打印件）基线解码 `decode_error`
- **分析**：不是二维码损坏——二维码在照片里占约 2300×2300 像素（每模块 ≈ 92 px），问题在成像尺度与噪声的组合
- **处置**：增加 decoder 内部降采样搜索 profile，同时**保留原基线**，两条路径并存
- **结果**：降采样读出，且与预先固定的答案**逐字节相同**（`truth_check.status = correct`，`exact_payload_bytes`）
- **证据**：`data/reports/qr-A7-downscale-001.json`

### 故事 2：本地全过、CI 全红

- **现象**：首次接入 GitHub Actions，`Run tests` 失败，282 passed / 1 failed
- **分析**：失败用例断言「必须运行在虚拟环境内」，而 `actions/setup-python` 提供的是全局 toolcache Python；这是**本地永远为真**的假设
- **处置**：没有给测试加 `skipif CI`（项目规则明确禁止弱化测试），而是在 workflow 中创建真实 venv
- **结果**：CI 转绿；**失败的提交保留在历史里**，作为真实的工程痕迹
- **证据**：提交 `581a657`（失败）→ `7bd4f4e`（修复）

### 故事 3：CI 全绿、本地报错

- **现象**：新增闸门后，pytest 出现 2 个 warning，原因是 `subprocess` 读取线程抛 `UnicodeDecodeError: 'gbk' codec ...`
- **分析**：闸门用 `subprocess.run(..., text=True)` 未指定编码，在中文 Windows 上按 GBK 解码子进程的 UTF-8 输出（含中文 `source` 字段）
- **处置**：显式 `encoding="utf-8", errors="replace"`
- **结果**：warning 归零；**这是 Linux CI 永远不会暴露的问题**——与故事 2 方向正好相反
- **证据**：提交 `eaca762` 内的修复与注释

### 故事 4：我的数据集假设是错的

- **现象**：第一版合成数据集 20 样本/split，`paired_change.improved = 0`——完全没覆盖降采样路径
- **分析**：初始假设是「大画面 + 小二维码能触发收益」，实测 200 px 二维码放在 1600×1200 里基线直接读出
- **处置**：回到 A7 数据反推真实触发条件——**每模块像素尺寸大 + 传感器噪声**；按修正模型扫描出 5 个有效配方
- **结果**：新增 `noise-large` 族后 `improved = 3`，把只有实拍才有的恢复路径变成 CI 可回归的样本
- **证据**：`docs/stage-33-synthetic-regression-dataset.md` 第 1–2 节

### 故事 5：退出码分不清「业务结果」和「程序故障」

- **现象**：`development` split 返回 `exit=2 / status=completed_with_errors`
- **分析**：`src/evaluate_labels.py` 对硬失败与「有样本按预期读不出」**返回同一个退出码 2**，CI 无法区分——这恰好违反项目自己的约束「区分业务结果与程序异常」
- **处置**：不改产品退出码语义（那属于另一个契约变更），而是新增闸门脚本，**只看报告 JSON**，与入库期望逐项精确比对
- **结果**：闸门正向通过、反向测试能失败；`improved` 变化（无论变好变坏）都必须 `--refresh` 并人工确认
- **证据**：`tools/check_evaluation_expectations.py`、`data/manifests/evaluation-synthetic-expectations.json`
