# Stage 07 读帧失败事件记录

## 1. 阶段目标

当已经打开的摄像头突然读取画面失败时，除了在终端显示提示，还把失败时间、最后成功帧号、事件类型和说明保存到独立 CSV。

本阶段只记录 `read_failed`，不实现自动重连、摄像头打开失败记录或故障分类。

## 2. 输入和输出

- 输入：最后一个成功显示的帧号、事件类型 `read_failed` 和错误说明。
- 输出：`data/reports/camera_events.csv` 中的一行事件。
- 字段：`recorded_at`、`frame_count`、`event`、`message`。

`frame_count` 表示失败之前成功处理了多少帧，不是失败帧自身的编号。

## 3. 为什么使用独立事件文件

`camera_quality.csv` 每行保存一帧的图像质量数值，`camera_events.csv` 每行保存一次采集事件。两种数据的字段和含义不同，分开保存可以避免一张表中出现大量空列，也便于后续诊断程序分别读取质量数据和采集链路事件。

## 4. 实现流程

1. 主循环调用 `cap.read()`。
2. 如果 `ok` 为假，先在终端显示失败信息。
3. 调用 `append_camera_event()` 追加 `read_failed` 事件。
4. 在终端显示事件文件路径。
5. 跳出循环，由 `finally` 释放摄像头并关闭窗口。

## 5. 修改的文件

- `src/report.py`：新增摄像头事件追加函数和默认事件报告路径。
- `src/camera_test.py`：在读帧失败分支记录事件。
- `tests/test_report.py`：验证事件目录、字段、毫秒时间和表头只写一次。

## 7. 易错点

- 打不开摄像头和打开后读帧失败是两种不同情况，本阶段只处理后者。
- `frame_count` 是最后成功帧数量，不会在失败时增加。
- 事件报告与质量报告的表头不同，不能混写到同一个文件。
- 如果用 Excel 打开事件 CSV，Windows 也可能阻止程序追加写入。
- 即使事件写入或读取过程出现异常，仍应通过 `finally` 释放摄像头。

重新运行后终端正常记录事件并释放资源，事件文件新增：

结果与修改的50帧条件一致。实验后已删除临时条件，正式代码恢复 `if not ok`。

## 9. 练习

1. 为什么事件记录不直接写进 `camera_quality.csv`？
2. 失败事件中的 `frame_count` 代表什么？
3. 为什么记录失败事件后仍然需要 `finally`？

本人能够解释：质量报告保存一帧的亮度和清晰度等指标，事件报告保存故障类型和说明。两种数据字段不同，混在一起会产生空列，也不利于人和后续程序读取。

事件中的 `frame_count=100` 表示失败前已经成功处理了100帧，失败的那一帧没有计入。

即使事件 CSV 写入过程也发生异常，`finally` 仍会释放摄像头并关闭窗口，避免设备继续被占用而影响下一次运行。
